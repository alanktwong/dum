# Design: Adopt mise as the Dev Toolchain Manager

Date: 2026-10-18
Status: Approved
Review amendments: 2026-10-29

## Goal

Adopt [mise](https://mise.jdx.dev) as the single source of truth for this
repository's development toolchain. mise replaces Homebrew (dev dependencies),
nvm (node), the Makefile (task entry point), and direnv (environment
activation). `tools/build.sh` and `tools/lib/*.sh` remain the recipe core; mise
tasks shell out to them.

Non-goals:

- No changes to the dum product itself: no new task type, no `dum.yml`
  playbook edits, no bootstrap that installs mise through dum.
- The release flow is otherwise unchanged: tags still trigger GoReleaser;
  `.svu.yml` and `.commitlintrc.yml` are untouched. One exception: the
  `make generate` hook inside `cfg/goreleaser.yaml` must be repointed (Section
  5) or the tag-push release pipeline fails once the Makefile is gone.
- pre-commit stays as the hook framework; its config is not rewritten.

## Current State

- Homebrew installs 13 tools in `setup_install_tools` (`tools/lib/setup.sh`):
  direnv, git-lfs, go, golangci-lint, goreleaser, jq, mockery, pre-commit,
  shellcheck, svu, trufflehog, yamlfmt, yq. Three more come from `go install`:
  go-enum, goimports, go-test-coverage.
- `setup_check_tools` follows nvm from `.nvmrc` (node 22) and hardcodes a
  `$GOPATH/bin` PATH requirement. Node exists only for the commitlint
  pre-commit hook.
- direnv owns environment activation via `.envrc`: git-lfs setup, pre-commit
  hook installation, `dotenv_if_exists` loading `.env`.
- The Makefile is a thin wrapper that dispatches every target to
  `tools/build.sh`; the real recipes live in `tools/lib/*.sh`.
- CI (`ci.yml`, `common.yml`, `release.yml`) uses `actions/setup-go@v5` pinned
  to `1.26` and `make ci-setup` (four `go install` calls).

## Section 1 — mise.toml

A `mise.toml` at the repository root becomes the source of truth for tool
version requests, environment settings, and task entry points; `mise.lock`
records exact resolved versions plus artifact URLs and checksums where the
selected backend provides them.

### Tools (`[tools]`)

| Tool | Source in mise | Replaces |
|------|----------------|----------|
| `go` | mise core, `"1.26"` | brew go; matches `go.mod` (1.26.5) and today's CI pin |
| `node` | mise core, `"22"` | `.nvmrc` + nvm in `setup_check_tools` |
| `python` | mise core, `"3.13"` | Python runtime required by the mise-managed `pre-commit` zipapp |
| `git-lfs`, `golangci-lint`, `mockery`, `goreleaser`, `svu`, `trufflehog`, `jq`, `yq`, `shellcheck`, `pre-commit`, `yamlfmt` | mise backends (prefer `aqua:` / `github:` for release binaries; use an appropriate package backend for Python-distributed tools; Mike Farah's `yq`) | corresponding brew entries |
| `go-enum`, `goimports` | `go:` backend (e.g. `go:github.com/abice/go-enum`) | `go install` in `setup_install_tools` and `setup_ci_tools` |
| `go-test-coverage` | `go:` backend (`go:github.com/vladopajic/go-test-coverage/v2`) pinned to `2.19.0` for Go 1.26 compatibility | `go install` in `setup_install_tools`. CI uses the `vladopajic/go-test-coverage@v2` action, not the local binary |

Use current literal backend prefixes; do not select the deprecated `ubi:`
backend. Exact tool-to-backend mappings are resolved during implementation;
the contract is **brew/homebrew is no longer a project dev-tool dependency** —
`mise install --locked` provisions all project tools, including git-lfs. The
selected Aqua `pre-commit` backend is a Python zipapp; pin Python 3.13 through
mise and validate `python3` in `check_tools` rather than relying on host Python.
`direnv` is removed rather than replaced by another install target.

The two `go-enum` `//go:generate` directives invoke the `go-enum` executable
from `PATH`, not `go run ...@latest`; this makes the mise-locked generator
version effective for `generate`, `build`, and the GoReleaser hook.

Use existing version requests where present (`go = "1.26"`, `node = "22"`).
For currently unpinned tools, use `latest` requests except `go-test-coverage`:
pin it to `2.19.0`, whose module requires Go 1.26. Versions `2.20.0` and
`2.21.0` require Go 1.27 and cause Go's automatic toolchain download, outside
the project lock. Upgrade this pin only with a Go baseline update or a verified
binary backend. Commit a generated `mise.lock` so local machines and CI resolve
the same exact versions and available checksums. Tool updates become deliberate
`mise lock --bump <tool>` changes, followed by validation and review.

### Settings and lockfile

Set `[settings] lockfile = true` so mise maintains the project lockfile, and
commit `mise.toml`, `mise.lock`, and any `.mise/locks/` sidecars generated by
mise. Mise does not preserve dependency declaration order; explicit `wait_for`
constraints below preserve the required task sequence.

Supported platform matrix is Linux and macOS on x64 and arm64, matching the
project's GoReleaser build targets. Generate lock entries for all four tuples
with `mise lock --platform linux-x64,linux-arm64,macos-x64,macos-arm64`.
Verify `mise install --locked` on each tuple; locked installation fails when
the current platform lacks a lock entry or required artifact URL.

### Environment (`[env]`)

mise injects tool paths per project. This replaces the `$GOPATH/bin` PATH
check in `setup_check_tools`. The repo's `.env` (optional local dotenv file)
continues to load via mise's project environment directive
(`[env] _.file = ".env"`), replacing direnv's `dotenv_if_exists`.

### Tasks (`[tasks]`)

Mise tasks expose the supported Make targets: `install`, `check`, `check_tools`, `clean`,
`tidy`, `vendor`, `generate`, `build`, `linters-build`, `release`,
`release-build`, `tag`, `lint`, `vet`, `fmt`, `fix`, `test`, `coverage`,
`check-coverage`, `profile`, `bench`, `all`, `help`. The Makefile's dependency
edges are load-bearing and are replicated with mise task `depends`, matching
the Makefile exactly:

- `build` depends on `fmt`, `vendor`, `generate`; its recipe is
  `./tools/build.sh make_out && ./tools/build.sh build` (the Makefile recipe
  runs `make_out` to create the gitignored `dist/` before the dispatcher
  builds into it; without it fresh-clone and CI builds fail).
- `vendor` depends on `tidy`.
- `test` depends on `build`.
- `coverage` and `check-coverage` depend on `test` (only dispatcher `test`
  produces `$OUT_DIR/cover.out`; both read it).
- `lint` depends on `build`; `release-build` depends on `build`.
- `check` depends on `build`, `fmt`, `fix`, `lint`, `vet`, `test`,
  `check-coverage`.
- `all` depends on `build` and `check` (dispatcher's `all` subcommand is only
  an announcement, so the mise task must carry the edges).

Tasks backed by dispatcher subcommands invoke `./tools/build.sh <subcommand>`;
common defaults in `tools/lib/common.sh` provide values formerly exported by
the Makefile (`OUT_DIR`, `DUM_VERSION`, etc.). The `build` task additionally
creates `dist/` before calling the build subcommand. No recipe logic moves into
mise. `tag` continues to run `svu next --tag` directly; `help` maps to
`mise tasks ls` rather than the awk helper.

Mise can run independent `depends` tasks concurrently and does not use the
declaration list as an ordering contract. Add explicit `wait_for` constraints
that only take effect when both tasks are already in the run graph:

- `tidy` waits for `fmt`; `generate` waits for `vendor`. This orders the build
  chain as format → tidy/vendor → generate → build while preserving standalone
  `vendor` and `generate` behavior.
- `fix` waits for `build`; `lint` waits for `fix`; `vet` waits for `lint`; and
  `test` waits for `vet`. This preserves `check`'s order after its shared
  `build`/`fmt` prerequisites.
- `check` waits for `build`, preserving `all`'s build-then-check order.

Validate ordering and shared-task de-duplication with mise's task graph and a
dry run before deleting the Makefile.

Excluded on purpose, with no equivalent mise task: `ci-setup` (superseded by
mise-action in CI; the dispatcher case and `setup_ci_tools` are both removed),
`print-go-version`, `rhard` (git variant), `make_out` (absorbed into the
  `build` recipe), `coverage-check` (dispatcher-only command), and
  `check-lfs-hook`.
`check-lfs-hook` is invoked directly by the local pre-commit hook as
`./tools/build.sh check-lfs-hook`, which keeps working without a task.

## Section 3 — Local Developer Flow

The current maintainer already has mise installed (`mise --help` succeeds), so
no mise installation step is needed for this migration. README still explains
one-time installation for new contributors.

1. One-time bootstrap for contributors without mise: install it using a
   supported method from mise's installation guide (Homebrew is optional, not
   a project dependency).
2. In the repo: `mise trust && mise install --locked`.
3. Shell activation: document `eval "$(mise activate bash)"` or
   `eval "$(mise activate zsh)"` for bash/zsh, and
   `mise activate fish | source` for fish. Add the matching command to the
   user's shell rc and replace the direnv hook line. Activation makes mise
   tools and optional `.env` available on cd, including for Git hooks that
   invoke system tools. Explicit `mise run ...` tasks work without activation.
4. `mise run install` configures Git LFS (`git lfs install --force`) and
   installs pre-commit hooks (`pre-commit install`,
   `pre-commit install --hook-type commit-msg`), taking over `.envrc`'s duties.

After migration, users with a stale `direnv hook` line in their rc lose
`.envrc` silently (`__PROJECT_DIRENV_INSTALLED` disappears). The README setup
flow must call this out explicitly.

## Section 4 — CI

`ci.yml`, `common.yml`, and `release.yml` swap `actions/setup-go@v5` for
`jdx/mise-action@v5`. With the checked-in lockfile, the action installs
mise-managed tools in locked mode; `ci-setup` is removed. `common.yml` exposes
a boolean `cache` input, defaulting to `true`, and passes it to the mise action.
The release caller sets it to `false` for the common setup job and the release
job's own mise action also sets `cache: false`; release jobs must not trust a
restored cache of installed tools. The common setup job has read-only contents
permission. Every other `make X`
invocation in the workflows becomes `mise run X` (`generate`, `build` in
`ci.yml`). `go mod download` remains.

Two CI tools remain deliberate external-action exceptions and are not governed
by `mise.lock`: `vladopajic/go-test-coverage@v2` and GoReleaser. The release
workflow keeps `goreleaser-action@v6`, which downloads its own GoReleaser
version (the action's `~> v2` default); it does not use the separately
mise-installed, lockfile-pinned `goreleaser`. This preserves the existing
release flow and narrows the exact-version guarantee to tools invoked through
mise-managed `PATH` or `mise run`.

## Section 5 — Release Flow

Unchanged gates: squash-merge with conventional titles → tag push →
GoReleaser. The only edit is `cfg/goreleaser.yaml`'s `before.hooks` (Section
2). The hook is repointed to `./tools/build.sh generate` rather than
`mise run generate` so GoReleaser does not require mise on PATH if the config
is ever used outside the mise-action'd release job; in the release job mise
and Go are on PATH either way. The local `mise run release` task keeps calling
`./tools/build.sh release` unchanged. The release action's GoReleaser binary
remains an explicit exception to `mise.lock`; local release-build tasks use the
mise-locked GoReleaser.

## Section 6 — Risks

- **direnv dropout**: existing shells stop loading `.envrc` after the file is
  removed. README must tell users to replace their direnv shell hook with mise
  activation; `check_tools` must give a clear `mise install --locked` remedy
  when a configured command is missing.
- **mise trust**: first use in the repo requires `mise trust`; documented.
- **Task ordering**: mise can run independent dependencies concurrently and
  does not guarantee declaration order; explicit `wait_for` constraints and
  dry-run verification preserve Make's side-effect-sensitive sequence.
- **Backend availability**: selected mise backends may lag versions for
  trufflehog, yamlfmt, or go-test-coverage; verify installability on Linux/macOS
  x64/arm64 before locking. If a tool lacks a suitable backend, use mise's
  `go:` backend where appropriate; no Homebrew fallback.
- **CI caching**: `actions/setup-go` module cache is lost; `mise-action` has
  its own caching and Go toolchain cache locations differ. Each action run
  installs the full configured `[tools]` set, including local-only tools not
  used by that job; measure cold/warm install time and cache size on both
  operating systems. The release setup and publishing jobs disable
  mise-action's installed-tool cache because restored tools are trusted without
  rechecking against `mise.lock`; the common setup job also has read-only
  contents permission. Add a CI tool allowlist or `go-cache` helper only if
  measurements show a noticeable regression.
- **Worktrees**: git worktree checkouts are separate directories; mise
  activation is per-directory, so each worktree is trusted/installed
  independently. No `.envrc` shim is added; acceptance is that
  `mise install` in a worktree just works.
- **Windows**: unchanged — the repo only supports macOS/Linux.
